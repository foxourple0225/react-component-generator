# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하거나 일부만 골라 적용하지 마라.**

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 처리)
- 유틸 함수
- **버그 수정** (재현하는 실패 테스트를 먼저 작성)
- 동작 변경이 있는 리팩터링

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업, 스타일)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **필수로 간주**한다.

## RED - GREEN - REFACTOR 사이클

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 테스트 이름은 동작을 설명한다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니므로 먼저 고친다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 고친다.

### 2. GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** - 지금 테스트가 요구하지 않는 것은 만들지 않는다.
- **신규 테스트와 기존 테스트를 모두 실행**해 전부 통과하는지 확인한다.
- 이 단계에서 구조 개선을 시도하지 않는다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 수행한다.
- 모든 테스트가 **green을 유지**해야 한다. 변경마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 새 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 다시 시작한다.
- "참고용"으로 남기거나, 주석 처리하거나, 테스트를 끼워 맞추려고 보면서 다시 쓰는 것도 **금지**다. 삭제는 삭제다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 먼저 바뀌고 가장 자주 조용히 깨진다. 테스트는 30초면 쓴다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 버그까지 통과시킨다. 그리고 나중은 오지 않는다. |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. 급할수록 테스트가 시간을 번다. |
| "삭제하면 낭비다" | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 것이 진짜 낭비다. |
| "프로토타입이다" | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 테스트 없이 써도 되지만, 남길 코드는 TDD다. |
