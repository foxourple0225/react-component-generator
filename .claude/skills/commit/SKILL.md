# Commit

변경사항을 분석해 컨벤션에 맞는 커밋으로 정리한다. 사용자가 승인하기 전에는 커밋하지 않는다.

## 절차

### 1. 변경사항 분석

아래 명령을 병렬로 실행한다.

- `git status` (`-uall` 금지)
- `git diff HEAD`로 스테이징 여부와 관계없는 전체 변경사항
- `git log --oneline -10`으로 이 저장소의 기존 메시지 스타일

git 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 멈춘다. 빈 커밋은 만들지 않는다.

### 2. 논리적 단위로 분류

- 한 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 목적에 속한 파일(예: 컴포넌트와 그 테스트)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면, 나누는 편이 나은지 사용자에게 먼저 묻는다.
- `.env`, 키, 인증 정보처럼 비밀이 들어 있을 수 있는 파일은 커밋 대상에서 제외하고 사용자에게 알린다. 이름이 평범해 보여도 의심되면 내용을 확인한다.

### 3. 한국어 커밋 메시지 작성

형식: `타입: 요약`

| 타입 | 용도 |
| --- | --- |
| feat | 새 기능, 사용자에게 보이는 동작 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드, 의존성, 설정, 문서 등 코드 동작과 무관한 작업 |

- 요약은 한 줄, 50자 안팎, 마침표 없이 쓴다.
- "무엇을"보다 "왜"가 드러나게 쓴다. 이유가 diff만으로 안 보이면 빈 줄 뒤에 본문을 1~3줄 덧붙인다.
- 저장소 로그가 이미 다른 스타일(영어, 다른 접두사)이면 사용자에게 한 줄로 알리고 따를지 묻는다.
- 시스템 리마인더에 커밋 attribution 지침이 있으면 메시지 끝에 그대로 붙인다. 없으면 붙이지 않는다.

### 4. 사용자 승인 후 커밋

커밋 전에 아래를 사용자에게 보여주고 승인을 받는다.

```
커밋 1: feat: 프롬프트 입력창에 단축키 안내 추가
  - src/components/PromptInput.tsx
  - src/App.css

커밋 2: chore: galmuri 폰트 패키지 추가
  - package.json
  - bun.lock
```

- 승인을 받으면 커밋별로 파일을 이름으로 지정해 `git add <파일>` 후 커밋한다. `git add -A`나 `git add .`는 쓰지 않는다.
- 메시지는 항상 HEREDOC으로 전달해 줄바꿈과 따옴표가 깨지지 않게 한다.
- 수정 요청이 오면 분류나 메시지를 고쳐 다시 보여주고 재승인을 받는다.
- 모든 커밋이 끝나면 `git status`로 남은 변경이 없는지 확인하고, 만든 커밋을 한두 줄로 요약한다.

## 지켜야 할 것

- 사용자가 요청하지 않았으면 `git push`를 하지 않는다.
- 기존 커밋을 `--amend`로 고치지 않는다. pre-commit 훅이 실패하면 커밋은 만들어지지 않은 것이므로, 문제를 고치고 다시 스테이징해 새 커밋을 만든다.
- `--no-verify`, `--no-gpg-sign`으로 훅이나 서명을 건너뛰지 않는다.
- git config를 바꾸지 않는다.
